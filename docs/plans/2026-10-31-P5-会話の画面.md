## 1. 概要

試験のシーンを、ミルダと話す場面だけ「会話の画面」で遊べるようにする。画面は上に NPC のカード（絵・名前・肩書）、真ん中にチャットのような会話、下に自分のキャラクターのカードと手札を並べる。会話は台詞を1つずつタップして読み進め、読み終えると手札が出る。手札を出すと自分の台詞も会話に足される。ギルドの扉を開けるところは今の紙面のまま。

そのために、シナリオに「紙面」と「会話」の2つの見せ方、NPC、台詞の行、絵（アイコンか画像）、カードの自分の台詞を足し、遊んだことの並び（プレイログ）を `PlayState` に仮の形で持たせる。

### 決めたこと

- **D1 シーンの見せ方**（`packages/domain/src/scenario/model.ts`）
  - `sceneSchema` を `layout` で分ける `z.discriminatedUnion`：
    - `layout: 'paper'`：`id`・`title`・`text`（段落の配列。P4 と同じ）・`hand`
    - `layout: 'conversation'`：`id`・`title`・`lines`（台詞の行の配列。1行以上。各行は `speaker`（NPC の id）と `text`）・`hand`
  - `layout` は省略できない（既定値を持たない。どちらの見せ方かをデータから必ず読めるようにする）。既存のシーンは `layout: 'paper'` を足す
  - `speaker` が指すのは `npcs` の id。参照の切れは `scenarioSchema` の `superRefine` で止める（P4 と同じ方針。読むすべての経路で止まる）。誤りの `path` は `scenes.1.lines.0.speaker` のように場所を指す
  - zod 4.6.7 の挙動（node_modules で確かめた）：`discriminatedUnion` は判別の値が合わないと `path` に判別のキー（`layout`・`type`）を付ける（`layout` が無い・未知なら `scenes.0.layout`）。形の誤りが1件でもあると `superRefine` は走らない。「形の誤りと参照の誤りを同時に報告する」ものではない。余分なキー（`layout: 'paper'` に `lines` を入れるなど）は既定では捨てられて通るので、シーンのオブジェクトは `z.strictObject` にして断る
- **D2 NPC と絵**
  - `scenarioSchema` に `npcs`（配列）を足す。`npcSchema`：`id`・`name`・`title`（肩書）・`description`（ひとこと。`NpcCard` が名前・肩書の下に小さく出す。幅が狭いときは隠す）・`portrait`。`id` は1文字以上
  - `portraitSchema` は `{ type: 'icon', name }` か `{ type: 'image', src }`（それぞれ `z.strictObject`。`type` と別の項目が混ざった形は断る）。`name`・`src` は1文字以上。ドメインは React を知らないので `name` は文字列のまま。NPC の id の重複と、予約語 `player` を id にすることを `superRefine` で止める。会話の行の `speaker` に `player` は書けない（`npcs` に無いので参照の切れになる。自分の台詞は `say` だけで表す）
  - 画面側（`apps/web/src/pages/pl/exam/ui/`）に `Portrait` を作る。`type: 'icon'` は `portraitIcons.ts`（`react-icons/gi` から使うものだけを import した、名前 → 部品の登録表）から引き、`type: 'image'` は `<img src alt={NPC の名前}>`。登録表に無い名前は `Portrait` が例外にする（シナリオの誤りを黙って隠さない。P4 の「シーンが見つからない」と同じ）。シナリオの NPC の `icon` の名前がすべて登録表にあることをテストで確かめる
  - 自分のカードの絵は、画面側の定数（共通のシルエットのアイコン）。ドメインのデータには持たせない
  - `react-icons` を `apps/web` の依存に足す。版は実装のセッションで、リリースから2週間以上経ったものを確かめて決める。アイコンの名前が実在することは `web:typecheck` が確かめる（`gi` から名前で import するため）。`portraitIcons.ts` はオブジェクトの表として書く（`export { … } from` は `noBarrelFile`・`noReExportAll` に当たる。`biome.json` の `noRestrictedImports` は `react-icons` を止めないことを確かめた）。`gi` は全アイコンが1つのモジュールにあるので、導入のときに `pnpm web:build` で使う名前だけが入っていること（ビルドの大きさ）を確かめる
- **D3 台詞の送り（画面の状態）**
  - 会話のシーンに入ると、最初の台詞が出ている状態から始める（プランで置いた既定。会話エリアが空のまま「次へ」だけが出るのを避けるため。人間レビューで変えてよい）。「次へ」ボタンを押すたびに1つずつ出る。出し切ると「次へ」が消え、手札と「続きは準備中です。」（手札が空のとき）が出る。出し切るまで手札は出さない
  - 送り位置は `ConversationScene` の `useState`（UI の状態）。`ExamPage`（実際には `Playthrough`。D6）が `<ConversationScene key={scene.id} …>` で描くので、シーンが変わるたびに部品ごと作り直されて最初に戻る。送り位置の `useState` を `key` を付ける側（親）に置かない（親の状態は `key` で戻らない）
  - 会話エリアは `role="log"`（新しい台詞が読み上げられる）。台詞の行の `key` は、本文でなく行の位置にする
  - 新しい台詞が出たら、会話エリアを下までスクロールする。`scrollIntoView` は jsdom に無いので使わず、会話エリアの要素の `scrollTop = scrollHeight` にする（T4 の最初に、jsdom で `scrollTop` の代入を確かめられるかを確かめ、確かめられなければ確かめを E2E（実ブラウザ）に移す）
  - 上の NPC カードは、そのシーンで直近に出た台詞の話し手を出す。純粋関数 `latestSpeaker(lines, revealed)`（`conversation.ts`。D5）で求める
- **D4 自分の台詞**：`cardSchema` に `say`（省略できる文字列）を足す。`{characterName}` は表示のときに置き換える（`renderText`）
- **D5 プレイログ（`PlayState.log`。仮の形）**
  - `logEntrySchema`：`sceneId`・`speaker`（NPC の id・`'player'`（定数 `PLAYER_SPEAKER`）・`null`（地の文））・`text`。`text` は `{characterName}` を置き換える前の形で持ち、表示のたびに置き換える（名前が決まった後も食い違わない）
  - `playStateSchema` に `log`（配列）を足す。`startPlay` は `[]`
  - `playCard` が、成功したときだけ、出したカードを出すシーンの内容をログの末尾に足す：紙面のシーンは各段落（`speaker: null`）、会話のシーンは各行（`speaker` は NPC の id）。続けて、カードに `say` があれば自分の台詞（`speaker: 'player'`）を足す。断った場合は `state` ごと返さないので、ログは増えない。入力の `state` は書き換えず、新しい `state` を返す（P4 と同じ）
  - ログに入るのは「出し切った台詞」だけ（手札が出るのは出し切った後なので、途中までの台詞をドメインは知らない）。いま遊んでいるシーンの台詞は、画面が送り位置まで描く
  - `packages/domain/src/scenario/conversation.ts`（会話の見せ方に関わる純粋関数）
    - `conversationHistory(scenario, state)`：会話エリアに出す履歴を返す。ログの末尾から、`sceneId` が会話のシーンの行が続く間だけを遡って返す（紙面のシーンの行に当たったら止める）。境界を表すフィールドは持たない（`sceneId` からシナリオを引けば決まる）。会話のシーンから会話のシーンへの移りでは途切れない
    - `latestSpeaker(lines, revealed)`：出した台詞（先頭から `revealed` 個）の最後の話し手の NPC の id。`revealed` は1以上、行数以下
  - 紙面のシーンで出したカードの `say` は、`sceneId` が紙面のシーンなので、履歴の範囲の外になる（紙面に自分の吹き出しは無い。今のデータの「受付へ進む」には `say` が無いので、当たらない）。仕様の文は「会話のシーンで出したカードの自分の台詞」とする（D8）
  - `renderText` の第2引数は `Pick<PlayState, 'characterName'>` に狭める（`PlayState` に `log` を足しても `text.test.ts` の入力が型エラーにならない）
  - イベントの列（core-loop）を作るときに、このログは置き換える。`docs/open-questions.md` の「遊んだことの持ち方」に、未決の中身として「会話の履歴を置く入れ物が、仮の形で `PlayState.log` にある。イベントの列に置き換えるときの形」を書く（実装の状態の記述は論点に置かない。コードの `log` のコメントと `docs/architecture/known-issues.md` に「仮」を書く）
- **D6 画面の構成**（`ExamPage` を `layout` で分ける。`pages/pl/exam/ui/`）
  - `ExamPage` は `adventurerExam` を読んで `Playthrough` に `scenario` として渡すだけにする。`Playthrough`（`PlayState`・名前を書くカード・断られた理由を持つ）は `scenario` を props で受け取る。画面のテストは `Playthrough` を、テスト用のシナリオ（`apps/web/src/test/screenScenario.ts`。`scenarioSchema.parse` を通す。`vi.mock` でデータのモジュールを差し替えない）で直接描く。ルート経由の描画（`renderAt`）は実データだけ
  - 紙面のシーン：今の画面のまま（`PaperScene`）。段落の `key` は本文でなく位置にする
  - 提案の「準備中（仮）」は、台詞を読んでいる間も出し続ける（押せない仮の表示で、手札の隣のまま。読んでいる間に本物の提案ができるかは、提案の保存の要望で決める）
  - 会話のシーン（`ConversationScene`）：
    - 上：`NpcCard`（絵・名前・肩書の横長の帯。D2 のひとことを小さく添える）。h1 はシーンの題のまま（どのシーンでも h1 はちょうど1つ）
    - 中：会話エリア。履歴（`conversationHistory`）の後に、いまのシーンの出た台詞を並べる。NPC の台詞は左、自分の台詞は右の吹き出し。残りの高さを占め、新しい行へ自動でスクロールする
    - 下：自分のカード（`PcCard`。名前か「（まだ名乗っていない）」と共通のシルエット）と手札。幅が狭いときは、自分のカードを手札の上の小さな帯にする
  - 名前の入力欄（`NameForm`）：会話エリアと手札の間に、今の登録用紙をそのまま出す。選んだときに記入欄へフォーカスを移す今の動きも残す
  - 提案の「準備中（仮）」：紙面・会話のどちらでも手札の隣
  - 見た目のトークンは P4 のデザインシステムのもの（`apps/web/src/app/styles/tokens.css`）。吹き出し・会話エリア・NPC の帯の役割は `docs/architecture/web-app.md`「デザインシステム」に足す
- **D7 シナリオの中身**（`adventurer-exam.json`。組み替えだけ）

## 8. スコープ外

- 台詞の間に自分のキャラクターが思ったことを書くメモ（別の要望 [play-log-notes](../backlog/play-log-notes.md)。このサイクルのログ `log` に「メモ」の種類を足す形で作る）
- 「章」の単位をデータに持つこと（宿のオープニングを書くときに決める）
- GM と PL のチャット（いまは対話の相手がいない。ノートに書くだけ）
- 手札のカードの絵・カードの絵柄の画像素材（`image` の型は作るが、実データはアイコンだけ）
- 台詞のタイプ演出・自動送り・送り位置を残して続きから遊ぶこと（続きから遊べる仕組みは未解決論点「遊んだことの持ち方」）
- 会話のシナリオに新しい台詞・新しいカードを足すこと（導線のカード「受付へ進む」と `say` の1行を除く）
- プレイログの保存（リロードで消える。P4 と同じ）。提案したシーンで読んだ台詞は、手札を出していないのでログに無い。提案の保存と続きからの再開（要望・未解決論点「遊んだことの持ち方」）で、提案のときにログへ何を足すかを決める
- 台詞を読んでいる間に本物の提案ができるか（読み切るまで提案できないか）。いまは仮の表示を出し続けるだけで、提案の保存の要望で決める
- 紙面のシーンで出したカードの自分の台詞を、会話の履歴に出すこと（いまのデータには無い）
- 名前の入力欄のチャット風の入力欄（人間レビューで要望が出たら）
- 提案のボタンと保存（playable-scene の別の要望）
