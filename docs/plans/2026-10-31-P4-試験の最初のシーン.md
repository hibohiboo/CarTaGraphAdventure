# 試験の最初のシーン

- 要望：[試験の最初のシーンで名乗れる](../backlog/exam-first-scene.md)
- 状態：手順1〜3（プラン作成・プランの AI レビュー・テスト網羅レビュー）が済んだ。レビューの P0・P1 はプランに反映した（「プランの AI レビューの結果」）。人間に確かめたことは「詳細設計」の「人間に確かめたこと」。レビューの後に名前の決まりも人間に確かめた（10 文字・見た目の1文字・仕様に書く）。次は手順4〜5（実装とテスト）を新しいセッションで、等級は標準（`sonnet`）。T1 から始める

## 1. 概要

`pnpm web:dev` で開いたアプリのホームから冒険者登録の試験に入り、受付のシーンで手札「名乗る」を出して、キャラクターの名前を書けるようにする。名前を書くと次のシーンで試験官が名前を呼び、「続きは準備中」で止まる。

画面の中身はシナリオの JSON から描く。そのために、シーン・手札・キャラクターの名前の最小の型（zod）と純粋関数を `packages/domain` に作る。

## 2. 背景

- 人間の要望（2026-10-31）：「`npm run web:dev` でプレイできる環境を作ってください。キャラクターの名前を入力するところまで」
- ロードマップ（`docs/roadmap.md`）は core-loop（ドメインで1シーンの遊び）→ playable-scene（ブラウザで遊べる）の順。今回は人間の判断で、core-loop の一部（型・純粋関数・シナリオの JSON）を最小で作り、その上に画面を載せる。イベントの列（core-loop の完成の条件2）は作らない。core-loop の完成の条件3「最初のシーンを JSON で表せる」は、この要望で先に満たされる（順の入れ替えの理由は D10 でノートに残す）
- 正式仕様：[遊びの共通の形](../cartagraph/index.md)「シーンですること」「キャラクター」、用語集の「シーン」「手札」「キャラクター」「冒険者登録の試験」
- 未解決論点（`docs/open-questions.md`）
  - 「遊んだことの持ち方」（イベントの列）… 触れない。状態は画面のメモリだけに持ち、リロードで最初に戻る
  - 「公開版での提案」… 触れない。提案のボタンを今回は出さない（下の D6）。ボタンの見せ方はこの論点が決着するまで固定しない
- デザイナーノート（`docs/notes/roadmap.md`「キックオフで決めたこと」）の「キャラクターの作り方」は「まず名前だけ」に決まっていて、ほかの案に「試験の最初のシーンを登録用紙（キャラクター作成）にする」がある。今回は、シーンの中で手札「名乗る」を出して名前を書く（人間が選んだ）。最初のシーンを丸ごと作成画面にする案とは別で、名前のほかは持たせない

## 3. 詳細設計

### 人間に確かめたこと（2026-10-31）

| 論点 | 決めたこと | ほかの案 |
|---|---|---|
| 範囲 | 最小のドメイン（型・純粋関数）とシナリオの JSON も作り、画面はそれを読んで描く | 画面だけ作り、文章は画面のコードに直書き |
| 名前を書く場所 | 受付のシーンで手札「名乗る」を出すと、名前の入力欄が出る | シーンの前の登録画面 |
| 名前を書いた後 | 次のシーンで試験官ミルダが名前を呼ぶ一文を出し、「続きは準備中です」で止まる | 入力欄までで止める |
| 手札 | 「名乗る」の1枚だけ。GM へ提案するボタンは出さない | ほかのカードを押せない形で並べる、押せて結果の文も出す |
| 名前の長さの上限（プランのレビューの後） | 10 文字。日本語として長い名前は不便なため | AI の案の 20 文字（仮） |
| 文字の数え方（同） | 見た目の1文字（書記素。`Intl.Segmenter` の `grapheme`）。Node 24・Chromium で使える | `Array.from` のコードポイント（結合文字は2、👨‍👩‍👧 は5、国旗は2と数え、見た目より多くなる） |
| 名前の決まりを仕様に書くか（同） | 書く（`docs/cartagraph/index.md`「キャラクター」）。正がプランとコードにしか無いと SSOT にならず、テスト7が `rule:` タグで指す仕様が無いため | プランとコードだけに置く |

### 決めたこと

- **D1 カードを出すときに名前を書く** — 「名乗る」は、出すときにキャラクターの名前を書くカード。名前の入力欄はカードを選んだときに出し、名前を確定すると、カードを出したことになって次のシーンへ進む。名前を書く専用のシーンは作らない（仕様の「シーンごとに、手札を出すか提案するか」のままにするため。この理由はノートに書き、仕様には書かない）
  - 仕様の追記（`docs/cartagraph/index.md`）
    - 「シーンですること」の「手札を出す」の項目の中に：「カードには、出すときにキャラクターの名前を書くものがある。名前を書いて出すと、それがキャラクターの名前になる」。2択の箇条書きの外に補足として足すと、「手札を出す」の定義との関係が読めないため、項目の中に入れる
    - 「キャラクター」の節に、名前の決まり（D2）を1行で：前後の空白を除いて1〜10文字、見た目の1文字で数える。見出しは変えない（`rule:index/シーンですること`・`rule:index/キャラクター` のタグを壊さない）
    - ページの末尾に、新しいノート `docs/notes/cartagraph.md` への1行のリンク（`docs/process/rules/spec-writing.md`）
  - ノート：`docs/notes/cartagraph.md` を作り、名前を書くカードにした理由（専用のシーンを作らない理由）と、上限を 10 文字にした理由（日本語として長い名前は不便）と、見た目の1文字で数える理由を書く。`docs/notes/index.md` の「ノートの一覧」と、`docs/.vitepress/config.mts` のノートのサイドバー（いまは「ロードマップ」だけ）にも足す
- **D2 名前の決まり** — 前後の空白（JS の `trim` が取るもの。半角・全角の空白、タブ、改行、NBSP）を取り除いてから、1〜10文字。空（空白だけ）と11文字以上は断り、入力欄の下に理由を出す。文字数は書記素（`Intl.Segmenter` の `grapheme`）で数える。保存する名前は取り除いた後の値。名前の途中の空白はそのまま通す。ゼロ幅の文字・制御文字は今回は特別に扱わない（スコープ外に書いた）。入力欄は1行の `<input>` なので改行は打てない。入力欄に `maxlength` は付けない（付けると打った文字が黙って切られ、ドメインの断る理由が出なくなる）
- **D3 シナリオの JSON の置き場所** — core-loop で決めることになっていた（`docs/process/rules/testing.md`「テストのデータ」、`docs/process/index.md`「適用範囲」）。`packages/domain/src/scenario/adventurer-exam.json` に置き、同じディレクトリの `adventurer-exam.ts` が zod で読んで（`parse`）書き出す。画面と E2E は `@cartagraph/domain/scenario/adventurer-exam` を import する（`package.json` の `exports` は `./*` → `./src/*.ts` なので、JSON を直接は指せない）
  - `resolveJsonModule` は足さない。TS 7.0.2 の `moduleResolution: bundler` で JSON の import が通り、型も推論されることを、プランのレビューで確かめた（domain の tsconfig を写した確かめ用のプロジェクト）。Vite・Vitest も JSON をそのまま扱う
  - **Playwright（E2E）から読めるかは未確認。** `apps/web` は `"type": "module"` で、Node の ESM は import 属性の無い JSON の import を断る。T3 で、E2E のファイルから `adventurer-exam` を import して1件流し、通るかを確かめる。通らなければ `adventurer-exam.ts` の import を `with { type: 'json' }` 付きにする（TS・Vite・Node のどれも受け付ける）。それでも通らなければ止めて報告する
  - 書き換える2か所：`docs/process/rules/testing.md`「テストのデータ」の「core-loop で決める」を、この置き場所に。`docs/process/index.md`「適用範囲」の「シナリオのデータの中身だけを直す変更はライト」は、データもスキーマも `packages/domain` に入るので、ファイルで線を引く：「`packages/domain/src/scenario/` の `*.json` だけを直す変更はライト。`.ts`（スキーマ・関数）を伴えばフル」
- **D4 ドメインの形**（`packages/domain/src/scenario/`。仕様のページは `docs/cartagraph/index.md`）
  - `model.ts`：`cardSchema`（`id`・`title`・`text`・`next`（次のシーンの id）・`asksCharacterName`（`.default(false)`））、`sceneSchema`（`id`・`title`・`text`（段落の配列）・`hand`（カードの配列。空なら続きは準備中））、`scenarioSchema`（`id`・`title`・`start`・`scenes`）、`playStateSchema`（`sceneId`・`characterName`（未定は null））
  - **参照の切れは `scenarioSchema` の `superRefine` で止める**（`refs.ts`・`findBrokenRefs` は作らない）。止めるもの：`start` とカードの `next` が指すシーンが無い、シーンの id の重複、同じ手札の中のカードの id の重複。`parse` の時に止まるので、`adventurer-exam.ts` を読むすべての経路（画面・テスト・E2E）で必ず止まる。別の関数にすると、呼び忘れた経路では止まらない（プランのレビューで、既存のツールで書けるかを比べた結果）。誤りの `path` は、切れた参照の場所（`scenes.0.hand.0.next` など）を指す
  - `transition.ts`：`startPlay(scenario)`、`playCard(scenario, state, cardId, characterName?)` → `{ ok: true, state }` か `{ ok: false, reason }`。断る理由は `unknownCard`（今のシーンの手札に無い）・`nameRequired`（名前が要るカードに名前が無い・空）・`nameTooLong`。確かめる順は `unknownCard` が先（無いカードに空の名前を渡したら `unknownCard`）。名前が要らないカードに名前を渡しても、名前は変えない。入力の `scenario`・`state` は書き換えず、新しい `state` を返す。`normalizeCharacterName(raw)` も同じファイル（引数は4つで、Biome の `useMaxParams` の上限ちょうど）
  - `text.ts`：`renderText(text, state)` が `{characterName}` を名前に置き換える。すべての出現を置き換え、名前の中の `$&` などを置換の特殊パターンとして解釈しない（`replaceAll` に関数を渡す）。名前が null なら置き換えずに残す。ほかの `{…}` には触れない
  - アーキテクチャルール「ディレクトリと依存の向き」の表に `scenario`（仕様ページ `index`）を足し、「いまはディレクトリが無い（`src/index.ts` は殻…）」の文を消す。`scenario` はほかのディレクトリを import しないので、`biome.json` にディレクトリごとの override は足さない（今の `packages/domain/src/**` の一律の禁止で足りる）。その override のメッセージの「表に無いディレクトリ」だけ、`scenario` を含む言い方に直す
  - ディレクトリの名前：`PlayState`・`transition.ts` はプレイの状態で、シナリオそのものではない。今は1つのディレクトリにまとめ、イベントの列（core-loop）を作るときに `play/` に分けるかを決める（表の行の仕様ページの欄では区別しない）
  - `src/index.ts`（殻）と `index.test.ts` を消す。Vitest 5 はテストが0件だと失敗するので、消すのは T2 の最初のテストを置くのと同じコミットにする
  - 集約とイベントは決めない（`docs/architecture/aggregates.md` は触らない）
  - `apps/web` の tsc は domain の `.ts` までたどって検査し、そのとき `apps/web/tsconfig.json` の `noUnusedLocals`・`noUnusedParameters` が domain のコードにもかかる。`domain:typecheck` だけでなく `web:typecheck` も通す
- **D5 画面** — ルート `/exam`（題名「試験のシーン」、グループ `pl`、`description`「冒険者登録の試験のシーンで、手札を出す」）を `routes.ts` と `app/router.tsx` に足す。ページは `pages/pl/exam/ui/ExamPage.tsx`。ホームの「まだ準備中です」を、`/exam` へのリンク「試験を受ける」に替える（リンク先のパスは `routes.ts` から引く。ルートの情報は `routes.ts` だけが持つ）

  - h1 はシーンの題（どのシーンでも h1 はちょうど1つ。`pages.test.tsx` が h1 を1つ要り、E2E とテストが「移った先にしか無い要素」として待てる）
  - シーンの段落（`renderText` を通す）を出し、手札をボタンで並べる。名前が要るカードを押すと、ラベル「キャラクターの名前」の入力欄と「この名前で名乗る」ボタンが出る（押す前は出さない。押しただけではシーンは進まない）。入力欄を閉じる取り消しは作らない。確定は Enter でもできる。断られたら理由（`nameRequired` と `nameTooLong` で別の文）を `role="alert"` で出し、入力は消さず、シーンは進めない。直して確定し直すと進み、理由は消える
  - 理由の欄は、理由があるときだけ描く（空の `role="alert"` を常に置かない。`e2e/smoke.test.ts` が初期描画で `alert` が0件であることを確かめる）
  - 名前は React の文字として出す（HTML として解釈しない）
  - 手札が空のシーンでは「続きは準備中です。」を出す
- **D6 提案のボタンは出さない（仮）** — 仕様では、どのシーンでも GM へ提案できる。今回は提案の保存（playable-scene の別の要望）が無いので、ボタンを出さない。画面のどのシーンにも、常に「GM への提案は準備中です（仮）」と出す（`docs/process/index.md` の8項目の3「仮」）。この文は `role="alert"` にしない。`docs/screens/index.md` の「できること」にも、提案はまだできないこと（PL-2 は未着手）を書く

## 5. 新規テストケース

ドメイン（`packages/domain/src/scenario/*.test.ts`）。仕様の節を確かめるものに `rule:index/シーンですること`（手札を出す）・`rule:index/キャラクター`（名前の決まり）のタグを付ける。`playCard` の分岐は、実データ（カードが「名乗る」1枚だけ）では作れない状況があるので、`scenarioSchema.parse` を通したテスト用の小さなシナリオ（2シーン・名前の要らないカード・別のシーンのカード）を使う。実データはテスト1・3・4・9 と画面に使う。断る場合のテスト（5〜7）は、入力の `scenario`・`state` を深く凍らせて渡し、書き換えないことと、戻りが `ok: false` で `state` を持たないことも確かめる。

1. `adventurer-exam` が `scenarioSchema` を通る。`start` のシーンがあり、`start` から全シーンに辿り着ける。名前が決まる前に辿り着けるシーン（`start`）の文に `{characterName}` が無く、名前の後のシーンの文にはある
2. `scenarioSchema` の参照の検査（`superRefine`）：実データを1か所だけ書き換えて、`start` が無いシーンを指す・カードの `next` が無いシーンを指す・シーンの id の重複・同じ手札のカードの id の重複は、それぞれ `safeParse` が失敗し、誤りの `path` がその場所を指す。書き換えない実データは通る（両側）
3. `startPlay` は `start` のシーンで、名前は null
4. `playCard`：「名乗る」に名前を付けて出すと、`next` のシーンへ進み、名前が入る（タグ）。名前の要らないカードに名前を渡しても、名前は変わらない（テスト用のシナリオ）
5. `playCard`：今のシーンの手札に無いカード（別のシーンのカード・無い id）は `unknownCard` で断る（タグ）。無いカードに空の名前を渡しても `unknownCard`（確かめる順）
6. `playCard`：名前が要るカードに名前が無い（`undefined`）・空文字・空白だけ（半角・全角の空白、タブと改行）は `nameRequired`
7. 名前の境界（表で書く。タグ `rule:index/キャラクター`）：1文字と10文字は通る、11文字は `nameTooLong`。前後の空白（全角の空白・タブを含む）を取り除いた後で数える（10文字 + 前後の空白は通る、11文字 + 前後の空白は `nameTooLong`）。保存される名前は取り除いた後の値。途中の空白は残る（`山田 太郎`）。サロゲートペアの絵文字 10 個は通り、11 個は `nameTooLong`。結合文字（`e` + U+0301）・ZWJ の絵文字（👨‍👩‍👧）・国旗を1文字に数える（それぞれ 10 個は通り、11 個は `nameTooLong`。コードポイントで数えると 10 個でも断るので、数え方の違いを区別できる）
8. `renderText`：`{characterName}` を名前に置き換える。同じ文の2つの `{characterName}` を両方置き換える。名前に `$&`・`$'` を含んでもそのまま出る。名前が null なら置き換えずに残す。ほかの `{foo}` は残す。期待値は固定の文字列で書く
9. 手札が空のシーン（`exam-begins`）では、どのカードも `unknownCard`

画面（`apps/web/src/test/examScene.test.tsx`。`renderAt` で描く）。文言はシナリオのデータ（`adventurer-exam`）から引く。ただし、名前の入った文の期待値を `renderText` で作らない（実装と同じ関数で期待値を作ると何も確かめない）

10. ホームの「試験を受ける」から受付のシーンの題（h1）と、シナリオの段落が出る。初期描画で `alert` が無く、名前の入力欄も無い
11. 「名乗る」を押すと入力欄が出て、h1 は受付のまま → 名前を書いて確定 → 次のシーンの h1 を待ってから、入力した名前を含む文が出ること・`{characterName}` の文字が画面に残っていないこと・「続きは準備中です。」が出ること・「名乗る」のボタンと入力欄が無いことを確かめる。受付のシーンでは「続きは準備中です。」が出ない（反対側）
12. 空白だけで確定すると `nameRequired` の理由が `alert` で出て、受付のまま、入力は消えない → 有効な名前に直して確定すると次のシーンへ進み、`alert` が消える
13. 11文字を打って確定すると、`nameTooLong` の理由（12 と別の文）が出て、受付のまま
14. 確定ボタンを2回続けて押す（`dblClick`）と、次のシーンのまま `alert` が出ない
15. 名前に `<b>x</b>` を入れると、文字のまま出る（太字の要素ができない）
16. 「GM への提案は準備中です（仮）」がどのシーンにも出て、`alert` ではない。「提案」の名前のボタンが無い（スコープ外の混入を止める）
17. 次のシーンまで進んだ後に描き直す（`renderAt` で新しく描く）と、受付のシーンに戻る（状態をモジュールに持っていない）

E2E（`apps/web/e2e/usecases/pl-1-play-card.test.ts`、タグ `@PL-1`）

18. `page.goto('/')` は最初の1回だけ。ホームのリンクから入り、受付のシーンの h1 を待つ。ステップ「PL-1 名乗るを出す」で「名乗る」を押し、入力欄を待って名前を書いて確定し、次のシーンの h1 を待ってから、名前を含む文を確かめる。最後に同じステップの中で、コンソールの誤りが無いことと `alert` が0件であることを確かめる（人間が補えない進行を、画面から最後まで通す）。断られる流れは E2E に入れない（Vitest の 12・13）

## 8. スコープ外

- イベントの列・リロードしても続きから遊べること（core-loop。未解決論点「遊んだことの持ち方」）
- GM へ提案するボタンと、提案を要望のファイルに書く開発サーバーの口（playable-scene の別の要望）。PL-1 のほかの流れ「提案待ちのシーンでは出せない」も、提案が無いので扱わない
- 「周りを観察する」「問い返す」など、「名乗る」のほかのカード
- 名前のほかのキャラクターの情報、キャラクターが持ち込む手札
- 名前に入る文字の種類の制限（ゼロ幅の文字・制御文字・孤立したサロゲートなど）
- 集約・ドメインイベントの決定（`docs/architecture/aggregates.md`）
- 見た目の作り込み（カードの絵柄など）。素の HTML に近い見た目で出す
