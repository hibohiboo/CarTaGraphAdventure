# 提案の保存

- 要望：[GM へ提案した文章が、要望のファイルとして保存できる](../backlog/proposal-save.md)
- 状態：手順1（プラン作成）が済んだ。次は手順2〜3（プランの AI レビュー・テスト網羅レビュー）を新しいセッションで、等級は強い（`opus`）

## 1. 概要

どのビートでも、手札の隣の「GM への提案」のカードを押して文章を書き、提案できるようにする。提案は、開発サーバーの口（`POST /api/proposals`）が `docs/backlog/proposal-<日時>.md` の要望ファイルに書く。ファイルには、どのシナリオ・シーン・ビートの提案かと、そこまでに遊んだことのイベントの列が入る。提案したビートは「提案待ち」になり、要望ファイルの状態が「完了」か「見送り」になるまで手札を出せない。

そのために、遊んだことを最小のイベントの列（「カードを出した」「GM へ提案した」）で持ち、列を流し直すと同じ状態に戻る関数を `packages/domain` に作る。公開版（GitHub Pages）では提案のカードを出さないが、提案待ちの止めはビルド時の要望ファイルから効かせる。

### 決めたこと

- **D1 イベントの列**（`packages/domain/src/scenario/model.ts`・新しい `scenario/events.ts`）
  - `playEventSchema`：`type` で分ける `z.discriminatedUnion`
    - `{ type: 'cardPlayed', beatId, cardId, characterName? }`（名前は名前を書くカードのときだけ。正規化した後の名前）
    - `{ type: 'proposed', beatId, text }`（正規化した後の文）
  - `replay(scenario, events)`：`startPlay` から順に畳み込む。`cardPlayed` は `playCard` を当て、`proposed` は状態を変えない。`{ ok: true, state }` か `{ ok: false, index, reason }`（どのイベントで断られたか。ビートが今のビートと違う・`playCard` が断った）
  - 画面（`Playthrough`）は `PlayState` の代わりにイベントの列を `useState` で持ち、状態は `replay` で作る（列を正にする。「列を流し直すと同じ状態」が作りで保たれる）。`replay` が断ったら例外（今の「ビートが見つからない」と同じ扱い）
  - `PlayState.log` はそのまま（`replay` の結果に入る）。置き換えは core-loop の残り
  - 集約の文書：集約「プレイ」（中に持つもの：イベントの列。守る不変条件：イベントは今のビートで出せるものだけ）と、ドメインイベント「カードを出した」「GM へ提案した」を `aggregates.md`・`event-flows.md`・`implementation-patterns.md`（プレイはイベント履歴式）に書き、`use-cases.md` の PL-1・PL-2 の集約とイベントの列を埋める（**AI の既定**。名前はプランのレビューで見てもらう）
- **D2 提案の決まり**（新しい `scenario/proposal.ts`）
  - `PROPOSAL_TEXT_MAX_LENGTH = 4000`。`normalizeProposalText(raw)`：前後の空白を除き、空なら `textRequired`、書記素で4000を超えたら `textTooLong`。書記素の数え方は名前と同じものを使う（`transition.ts` の `Intl.Segmenter` を共用する小さな関数に切り出す）
  - `propose(scenario, events, text)`：今のビートの手札を読み切った後に呼ぶ前提で、正規化して `proposed` のイベントを足した列を返す（断る理由は文の決まりだけ）
  - `awaitingProposal({ proposals, events, beatId })`：そのビートの提案待ちの文の一覧を返す。`proposals` はビルド時に読んだ未完了の提案（`{ beatId, summary }`）、`events` はこのセッションで出した `proposed`。空なら提案待ちではない
  - `playCard` に、提案待ちのビートの集合を任意で渡せるようにし、そのビートでは `awaitingProposal` の理由で断る（PL-1 の「提案待ちのビートでは出せない」をドメインで守る。`replay` は渡さない：過去のイベントはその時に出せたもの）
- **D3 要望ファイルの形**（新しい `apps/web/vite/proposalFile.ts`。Node の組み込みだけ、domain を import しない純粋関数）
  - `renderProposalFile({ scenario, scene, beat, text, events, now })` が下の本文を返す。`title` は「提案：」＋文の1行目の先頭30文字（超えたら「…」）、`summary` は文の先頭100文字（改行は空白に。超えたら「…」）。`title`・`summary` は YAML の二重引用符の文字列（`JSON.stringify`）で書く（`:`・`#`・引用符で YAML が壊れないように）
  - `parseProposalFile(source)`：`proposal:` の `scenario`・`beat`、`status`、`summary` を読む。`proposal:` が無いファイル（ふつうの要望）は `null`
  - ファイル名は `proposal-YYYYMMDD-HHmmss.md`（ローカル時刻）。同じ名前があれば `-2`, `-3` … を付ける（`writeFile` の `flag: 'wx'` で、あったら次の番号）。ファイル名に利用者の入力を入れない

  試験官に試験の中身を聞きたい

  ## そこまでに遊んだこと

  イベントの列（`replay` で流し直すと、このビートの状態に戻る）。

  ```json
  [ … , { "type": "proposed", "beatId": "reception", "text": "…" } ]
  ```

- **D4 開発サーバーの口**（新しい `apps/web/vite/proposals.ts` の Vite プラグイン。`vite.config.ts` の `plugins` に足す）
  - `configureServer` で `POST /api/proposals` のミドルウェアを足す（開発サーバーだけ。preview・build には無い）
  - 受け付けの検査（順に。どれも `{ message }` で返す）
    1. 送り元：`req.socket.remoteAddress` がループバック（`127.0.0.0/8`・`::1`）かプライベートの IPv4（`10/8`・`172.16/12`・`192.168/16`。`::ffff:` の付いた形も）でなければ 403
    2. `Origin` があれば、その host が `Host` と同じでなければ 403（よそのサイトのページから、開いているブラウザ経由で書かれないように。**AI の既定**）
    3. 本文が 64 KB を超えたら 422（読み切る前に打ち切る）
    4. 本文の形（`packages/schemas` の `safeParseBodyText`）が合わなければ 422
    5. シナリオが無い、`replay` が断る、文の決まり（D2）に合わなければ 422（提案するビートは `replay` の終わりのビート。台詞を読み切ったかは画面の状態なので、口は見ない）
    6. 書けなければ 500
  - 成功は 201 `{ file }`（リポジトリの直下からのパス。例 `docs/backlog/proposal-20261031-153012.md`）
  - 本文：`{ scenarioId, text, events }`。`events` はこの提案の前までの列。口が `replay` で今のビートとシーンを決め、`proposed` を足してファイルに書く（本文にビートを持たせない。列と食い違わないように）
  - 検査とファイルの組み立ては `apps/web/vite/proposalHandler.ts`（`handleProposal({ remoteAddress, origin, host, rawBody, backlogDir, now })` → `{ status, body }`）に置き、プラグインは `server.ssrLoadModule` で読む（Vite の変換を通すので、`@cartagraph/domain`・`@cartagraph/schemas` の TS を import できる。`vite.config.ts` の読み込みには入れない）。**実装の最初に、`ssrLoadModule` で domain・schemas が読めることを確かめる**。読めなければ止めて報告する
  - 書く先の既定はリポジトリの `docs/backlog/`（`import.meta.url` から組み立てる）。テストは引数で一時ディレクトリを渡す
- **D5 提案待ちの一覧の読み込み**（同じプラグインの仮想モジュール `virtual:proposals`）
  - `load` で `docs/backlog/*.md` を読み、`parseProposalFile` が返したうち、状態が「完了」「見送り」でないものを `{ scenarioId, beatId, summary }[]` で出す（build でも dev でも。公開版でも止めが効く）
  - 開発サーバーでは、ページを開き直すたびに読み直す（`transformIndexHtml` で仮想モジュールを無効にする）。`docs/backlog/` の変更は見張らない：口が書いたファイルでページが読み直され、遊んだことが消えないように。人間が状態を「完了」にしたら、ページを開き直すと止めが外れる
  - 型は `apps/web/src/vite-env.d.ts` に `declare module 'virtual:proposals'`
- **D6 画面**（`apps/web/src/pages/pl/exam/ui/`）
  - `HandZone` の仮の表示を、押せる提案のカード（点線の枠のボタン「＋ GM への提案」）に替える。`canPropose` が偽（公開版）なら出さない。会話のビートでは、手札と同じく台詞を読み切ってから出る（`showHand` に従う）
  - 押すと、手札の上に提案の入力欄（新しい `ProposalForm`：見出し「GM への提案」、複数行の `textarea`、「やめる」「提案する」）。名前の入力欄とは同時に開かない（片方を開くともう片方を閉じる）
  - 「提案する」で、送っている間はボタンを押せなくする（二重送信を止める）。成功したら `proposed` のイベントを列に足して入力欄を閉じる。断られた・送れなかったら、入力欄を開いたまま文を残し、理由を出す（文の決まりは送る前に `normalizeProposalText` で画面が止める。口の 4xx・5xx・通信の失敗は「提案を保存できませんでした：<message>」）

## 5. 新規テストケース

ドメイン（`packages/domain`）

1. `replay` で空の列は `startPlay` と同じ状態
2. `replay`：実データで「扉を開ける → 受付へ進む → 名乗る（アリサ）」の列を流すと、画面で同じ順に出したときの `playCard` の結果と同じ状態（`beatId`・名前・`log`）
3. `replay`：`proposed` は状態を変えない（前後で同じ）
4. `replay`：今のビートと違う `beatId` のイベントは、その位置（`index`）で断る
5. `replay`：`playCard` が断るイベント（無いカード・名前が空）は、その位置と理由で断る
6. `normalizeProposalText`：前後の空白を除く／空と空白だけは `textRequired`／4000文字ちょうどは通る／4001文字は `textTooLong`／絵文字・結合文字は1文字で数える／改行は残る
7. `propose`：`proposed` を末尾に足した列を返す。文の決まりに合わなければ断る
8. `awaitingProposal`：一覧にそのビートがあれば文を返す／別のビートだけなら空／このセッションの `proposed` もそのビートなら入る
9. `playCard`：提案待ちの集合にあるビートでは `awaitingProposal` で断る／集合に無ければ今までどおり
10. `playEventSchema`：`type` が無い・未知の `type`・余分なキーを断る

要望ファイル（`apps/web/vite/proposalFile.ts`）

11. `renderProposalFile`：D3 の例の形（frontmatter のキー、`proposal`、`trace`、本文の見出し、JSON の列の最後が `proposed`）
12. `title`：1行目の30文字ちょうどは「…」なし、31文字は30文字＋「…」。2行目以降は入らない
13. `summary`：100文字の境界、改行は空白に
14. `title`・`summary` に `:`・`#`・`"`・`\` があっても、`parseProposalFile` と `scripts/trace.mjs` の `frontmatterValue` で読める（YAML が壊れない）

開発サーバーの口（`apps/web/vite/proposalHandler.ts`。`mkdtemp` の一時ディレクトリに書く）

17. 正しい本文で 201 と `{ file }`、一時ディレクトリにファイルが1つでき、中身の列を `replay` すると提案したビートに戻る

## 8. スコープ外

- 提案の要望を受け取ってシナリオか機能かに振り分ける手順、要望を完了にした後に提案のファイルの列から続きを遊ぶこと（proposal-loop）
- `PlayState.log` をイベントの列に置き換えること、提案したビートで読んだ台詞を残すか（未解決論点に残す）
- 遊んだことの保存（リロードで最初に戻る。P4・P5 と同じ）
- 公開版から提案を送る（GitHub Issue・コピーなど）
- 提案の文の編集・取り消し（要望ファイルを人間が直す・消す）
- 要望ファイルの自動コミット
- MSW のハンドラ（口は開発サーバーのプラグインで作る。画面のテストは送る関数を差し替える）
- 提案のカードの見た目の作り込み（今の点線の枠のカードを押せるようにするだけ）
