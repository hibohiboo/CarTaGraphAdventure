## 1. 概要

どのビートでも、手札の隣の「GM への提案」のカードを押して文章を書き、提案できるようにする。提案は、開発サーバーの口（`POST /api/proposals`）が `docs/backlog/proposal-<日時>.md` の要望ファイルに書く。ファイルには、どのシナリオ・シーン・ビートの提案かと、そこまでに遊んだことのイベントの列が入る。提案したビートは「提案待ち」になり、要望ファイルの状態が「完了」か「見送り」になるまで手札を出せない。

そのために、遊んだことを最小のイベントの列（「手札を出した」「GM へ提案した」）で持ち、列を流し直すと同じ状態に戻る関数を `packages/domain` に作る。公開版（GitHub Pages）では提案のカードを出さないが、提案待ちの止めはビルド時の要望ファイルから効かせる。口は Hono で書き、Vite プラグインで開発サーバーにつなぐ（これがバックエンドの代わりになる）。使っていない MSW は依存から消す。画面のテストは送る関数を差し替える。

### 決めたこと

- **D1 イベントの列と集約「プレイ」**（`packages/domain/src/scenario/model.ts`・新しい `scenario/events.ts`）
  - `playEventSchema`：`type` で分ける `z.discriminatedUnion`（`z.strictObject` で余分なキーを断る）
    - `{ type: 'cardPlayed', beatId, cardId, characterName? }`（名前は名前を書くカードのときだけ。正規化した後の名前）
    - `{ type: 'proposed', beatId, text }`（正規化した後の文）
  - 操作（命令）とイベントの当て方を分ける（`aggregates.md`「操作は純粋関数」：新しい集約と起きたイベントか、断る理由を返す）
    - 当て方：`replay(scenario, events)`：`startPlay` から順に畳み込む。`cardPlayed` は既存の `playCard` を当て、`proposed` は状態を変えない。`{ ok: true, state }` か `{ ok: false, index, reason }`（どのイベントで断られたか。ビートが今のビートと違う・`playCard` が断った）。過去のイベントはその時に出せたものなので、提案待ちは見ない
    - 命令：`decidePlayCard(scenario, events, { cardId, characterName?, awaitingBeatIds? })` と `propose(scenario, events, text)`（D2）。どちらも `{ ok: true, events, event }`（イベントを足した列と、足したイベント）か `{ ok: false, reason }`。`replay` が断る列を渡したら `{ ok: false, reason: 'invalidEvents' }`
    - `playCard` の引数は増やさない（`useMaxParams` の4。提案待ちの止めは `decidePlayCard` で守る）
  - 画面（`Playthrough`）は `PlayState` の代わりにイベントの列を `useState` で持ち、状態は `replay` で作る（列を正にする）。`replay` が断ったら例外（今の「ビートが見つからない」と同じ扱い）
  - `PlayState.log` はそのまま（`replay` の結果に入る）。置き換えは core-loop の残り
  - 集約の文書（**AI の既定**。名前は実装の AI レビューと人間レビューで見てもらう）
    - コンテキスト「プレイ」の集約「プレイ」：中に持つもの＝イベントの列。守る不変条件＝イベントは、その時のビートで出せるものだけ。保存はイベント履歴式（`implementation-patterns.md`）。いまは画面のメモリにだけあり、提案のファイルに写しが入る
    - ドメインイベント「手札を出した」（起こす＝プレイ、受け取る＝なし）、「GM へ提案した」（起こす＝プレイ、受け取る＝コンテキスト「提案の取り込み」が要望を作る）
    - いまの作り：口が `propose` で列を確かめて要望のファイルを書き（書き換えるのは要望だけ）、書けたら画面が列に `proposed` を足す（書き換えるのはプレイだけ）。保存できなかった提案を列に残さないため、受け取る側を先に書く。1回の操作で書き換える集約は、口・画面それぞれ1つ
    - 提案待ちは、要望の状態から作る読みモデル（`virtual:proposals`）として `event-flows.md` の「ポリシー・読みモデル」の列に書く
    - `aggregates.md`・`event-flows.md`・`implementation-patterns.md`・`bounded-contexts.md`・`domain-map.md`（「core-loop で決める」と書いた所）を直し、`use-cases.md` の PL-1・PL-2 の集約とイベントの列を埋める
- **D2 提案の決まり**（新しい `scenario/proposal.ts`）
  - `PROPOSAL_TEXT_MAX_LENGTH = 4000`。`normalizeProposalText(raw)`：前後の空白を除き、空なら `textRequired`、書記素で4000を超えたら `textTooLong`。書記素の数え方は `scenario/text.ts` に `countGraphemes` として切り出し、名前の決まり（`transition.ts`）と共用する
  - `propose(scenario, events, text)`：正規化し、`replay` の終わりのビートで `proposed` を足す（D1 の命令の形）。断る理由は文の決まりと `invalidEvents`
  - `proposalTitle(text)`：「提案：」＋1行目の先頭30書記素（超えたら「…」）。`proposalSummary(text)`：先頭100書記素（改行（CRLF も）は空白1つに。超えたら「…」）。どちらも `"` を `＂`、`\` を `＼` に置き換える（YAML の二重引用符の中でエスケープが要らなくなり、`frontmatterValue` と YAML のパーサーで同じ値になる）。要望ファイル（D3）と画面の提案待ちの一覧（D6）が使う
  - `awaitingProposal({ proposals, events, scenarioId, beatId })`：そのビートの提案待ちの文の一覧を返す。`proposals` はビルド時に読んだ未完了の提案（`{ scenarioId, beatId, summary }`。型は `PendingProposal` として domain に置く）で、`scenarioId` で絞る。`events` はこのセッションの列で、そのビートの `proposed` の文を `proposalSummary` で足す。空なら提案待ちではない
  - `decidePlayCard` は、`awaitingBeatIds` に今のビートがあれば `awaitingProposal` の理由で断る（PL-1 の「提案待ちのビートでは出せない」をドメインで守る）
- **D3 要望ファイルの形**（新しい `apps/web/vite/proposalFile.ts`）
  - `renderProposalFile({ scenario, scene, beat, screen, text, events, now })` が下の本文を返す。`ssrLoadModule` 経由で読む（domain の `proposalTitle`・`proposalSummary` を使う）
  - **プレイヤーの文は、コードブロックの中にだけ入れる**（VitePress は Markdown を Vue のテンプレートにするので、`{{ }}`・HTML のタグ・リンク・見出しが本文にあると、式の評価・`docs:build` の失敗・見出しの紛れが起きる。コードブロックは VitePress が `v-pre` にしてエスケープする）。フェンスは、中身のいちばん長いバッククォートの並びより1つ長くする（3つ以上）。題の見出しは利用者の文を入れず `# 提案（2026-10-31 15:30）` にする。`title`・`summary` は frontmatter の YAML の二重引用符の文字列（`JSON.stringify`）で、D2 の置き換えの後なのでエスケープが出ない
  - 読み戻しは `scripts/trace.mjs` を共用する（要望の frontmatter の読み手を1つに保つ）。`trace.mjs` に、入れ子のキーを読む `frontmatterNested(source, 'proposal')` を足し、`frontmatterValue` が CRLF の行末でも値を読めるようにする。`parseProposalFile(source)`（`trace.mjs` に置く）：`proposal:` の `scenario`・`beat`、`status`、`summary` を返す。`proposal:` が無いファイルと、`scenario`・`beat` が欠けたファイルは `null`。`apps/web` から import するため `scripts/trace.d.mts` を足す（`rule-sections.d.mts` と同じ形）
  - ファイル名は `proposal-YYYYMMDD-HHmmss.md`（ローカル時刻）。同じ名前があれば `-2`, `-3` … を付ける（`writeFile` の `flag: 'wx'`。`EEXIST` のときだけ次の番号へ。ほかの誤りはそのまま投げる。番号は100で打ち切って誤り）。ファイル名に利用者の入力を入れない
  - `milestone`・`trace` は人間が認めた例のとおり（`proposal-loop`、`PL-2` と画面）。振り分けるとき（proposal-loop）に人間が書き直す。画面のパスは、シナリオの id から引く表（D4）から入れる
