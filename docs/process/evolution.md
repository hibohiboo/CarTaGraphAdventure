# 開発体制の進化ログ

開発プロセス自体の変更を「候補 → 評価 → 採用／却下」の型で記録する。運用は[開発プロセス](index.md#体制の進化)が正。却下も削除せず理由付きで残す。

記録するのは「ルール・依頼文・スキル・サブエージェント・CI など、進め方に関する変更」であり、機能の設計判断はプランドキュメント（`docs/plans/`）に書く。

このページには、まだ評価していない候補と書き方だけを置く。評価を終えた候補と、採用・却下の記録は、月ごとのページ（`evolution/<年-月>.md`）に書く。[体制の進化のタイムライン](timeline.md)は月ごとのページから年表を組み立てる。

この仕組みは、前のリポジトリ（[CarTaGraphFantasy の進化ログ](https://github.com/hibohiboo/CarTaGraphFantasy/blob/main/docs/process/evolution.md)）から持ち込んだ。それより前の経緯はそちらにある。

## 候補（未評価）

サイクルの途中で気づいた人（人間・AIどちらでも）が追記する。書式：`- [ ] <候補> — <気づいた状況・根拠>（<日付>）`。評価したら、この行を `- [x]` にして、評価した月のページの「候補（評価済み）」へ移す。

- [ ] スクリプトのテストが、リポジトリの実物の docs に寄りかかっている — P1 の R8 で、元の実物（要望40件以上・`SC-1` など）を前提にしたテスト5件をこちらの実物に合わせたら、対象外の節を外すことの確かめが抜けた（実装レビューの A4）。R7 では、表が空だと `usecases.mjs`・`rule-sections.mjs` が止まった。1回目なので記録だけ。前の同種：なし。きっかけ：作業中の失敗と AI レビュー。止め方の案：手順（仕組みを確かめるテストはフィクスチャで書き、実物を読むテストは「読める」ことだけを見る、と `testing.md` に足す）（2026-10-30）
- [ ] 人間に判断を頼むときに添えた事実が、確かめたものではなかった — P3 のプランで2回起きた。D4 では「新しいテストの lint のルールは、いずれも `scripts/*.test.mjs`」と示したが、`apps/web/e2e/smoke.test.ts` にも当たっていた。D12 では「Vitest 5 が msw を引き込むようになった」と添えたが、main の lockfile（Vitest 4）でも既に入っていた。どちらも決定は変わらなかったが、誤った前提のまま人間が決めるおそれがあった。前の同種：なし（同じサイクルで2回）。きっかけ：プランの AI レビュー。止め方の案：手順（grilling スキルで質問に事実を添えるときは、確かめたコマンドと出力の要点を一緒に示し、確かめていないことは「未確認」と書く）。裏付け：P4 のプランの D3 は、Playwright から JSON を読めるかを「未確認」と明記し、確かめ方とだめなときの手を先に書いた。実装はその想定どおりに進み、手戻りが無かった（2026-10-31）
- [ ] 既定の重さが warning・info の lint のルールは、違反してもどこでも止まらない — P3 のプランで、Biome 2.6 の新しいテストの lint のルール3つが既定（info・warning）のままでは、コミットも CI も止めないことを見落としていた（プランの AI レビューで指摘され、override で error に上げた）。版を上げるたびに新しいルールが warning で入ると、気づかないまま違反が溜まる。1回目なので記録だけ。前の同種：なし。きっかけ：プランの AI レビュー。止め方の案：機械（`pnpm lint` と pre-commit を `biome check --error-on-warnings` にする。いまは `apps/web/src/main.tsx` の `noNonNullAssertion` の警告が1件あるので、先にそれを直すか、その1件だけ重さを決める）（2026-10-31）
- [ ] 人間が画面で見て分かるものを、人間に確かめずにスコープ外にした — P4 のプランで「見た目の作り込み（素の HTML に近い見た目）」を「人間に確かめたこと」の表に載せずにスコープ外にし、人間レビューで「ゲームらしくない」と差し戻された（D11 で前のリポジトリのデザインシステムを持ち込んだ）。人間によれば前のリポジトリでも同じ指示をしていた（人間の申告で、記録は確かめられていない）。前の同種：このリポジトリの進化ログにはなし。きっかけ：人間レビュー。止め方の案：置き場所（デザインシステムを `docs/architecture/web-app.md`「デザインシステム」に書いた。次の画面からはここに従う。再発したら、手順として grilling でスコープ外を決めるとき、画面に出るもの（見た目・文言・操作）は人間に確かめて「人間に確かめたこと」の表に載せる）（2026-10-31）

## 書き方

採用・却下は、その月のページ（`evolution/<年-月>.md`。無ければ作る）の「採用済み」「却下」の先頭に足す（新しいものを上に）。書式：`### <日付> <タイトル>` の下に、内容・理由・反映先と、次の2つを書く。却下は理由を必ず書く。

- **きっかけ** — 誰が・何で気づいたか：人間レビュー／AI レビュー／作業中の失敗／人間の要望／計画（基盤整備などのプラン）
- **止め方** — 同じことをどう防ぐか：機械（CI・git フック・lint・Claude Code のフック・ビルド時の検査や自動生成）／レビュー観点／手順・ルール（文書に書く）／置き場所（ページ・ファイルを新設・移動する）。複数あれば並べる

後から「改善がどこから生まれ、どれだけ機械で止められるようになったか」を辿れるようにするため。[体制の進化のタイムライン](timeline.md)が、月ごとのページの「採用済み」「却下」からビルド時に年表と内訳を作る。きっかけ・止め方は、まとめの1行（`- **きっかけ** — … ／ **止め方** — …`）か、小項目ごとの1行（`- きっかけ：… ／ 止め方：…`）で書く。読めないとビルドが止まる。止め方は最初の「。」（括弧の外）までを読むので、まだやっていない案は「。」の後ろに書く
