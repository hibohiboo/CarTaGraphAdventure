## 採用済み

### 2026-10-31 開発サーバーの口は LAN からも受け付け、MSW は使わない（P6）

提案の保存（P6）で、最初の API を作るにあたり、人間の判断で 2 つ決めた。(1) 開発サーバーの書き込みの口の受け付け先を、ループバックだけからプライベートの LAN にも広げた（スマホから提案できるように）。`review.md` 観点6を、送り元の範囲・`Origin` の確かめ・書く先・利用者の文の出方を見る形に直した。残るリスクは `web-app.md`「提案の口」に書く。(2) 「画面から API を叩く最初の要望で MSW のハンドラを作る」をやめ、API は開発サーバーの Vite プラグインの口（Hono）で受けて、MSW は依存・worker・`biome.json` の除外から消した（vitest の任意 peer として残る分は `pnpm-workspace.yaml` の `allowBuilds` で `false`）。`AGENTS.md`・`web-app.md` の文を直した。あわせて `architecture.md` に、`apps/web/vite/`（開発サーバーの口。`ssrLoadModule` で読むファイルだけ domain・schemas を import してよい）と `packages/schemas` の区切りのディレクトリ `proposals/` を書いた。口を実際に動かして `docs:build` を回すと、プレイヤーの文を frontmatter の `title`・`summary` に入れたとき `</script>` で VitePress が落ちた（プランのレビューは本文の入れ方だけを見ていた）。口の書いた文は frontmatter でも `<`・`>` を全角にする（ルールではなくコードで止める）。

- **きっかけ** — 計画（P6 のプランのレビューの後の人間の判断） ／ **止め方** — ルール（`review.md` 観点6）。MSW の持ち込みは依存の削除で止まる

### 2026-10-31 楽観ロックでリスクをとる。mutate-check は Red を見ずに通ったテストだけ

P5 では、プランの T2・T4 に mutate-check の項目を13個並べ、TDD で Red を見たテストにも重ねてかけた。`testing.md` が求めていたのは最初から通るテストだけで、上乗せはプランのレビューの指摘から入った。実装の AI レビューの P0 は0件だったが、手戻りの大半（配置・口調）は人間レビューで出ており、前段の重い確かめでは防げない種類だった。人間は「毎回過剰に確かめると速さが落ちる」と指摘し、前のリポジトリからの考え「楽観ロックでリスクをとる」（先にロックせず進め、ぶつかったときだけ直す）を示した。

`docs/process/index.md`「この章の設計原則」にこの考えを足した（失敗に気づいて戻せる仕組みがあるところでは、前段の関門を緩めてよい）。`testing.md`「骨抜き禁止」に、Red を見たテストには mutate-check をかけず、プランで項目を前もって並べないことを書き、依頼文「3」がそれを求めないようにした。

- **きっかけ** — 人間レビュー（P5 の振り返りでの指摘） ／ **止め方** — 手順・ルール（`docs/process/index.md`「この章の設計原則」、`testing.md`、依頼文「3」）。機械では止めない：Red を見たかどうかは、テストのコードからは決まらない

### 2026-10-31 画面の配置は図で確かめ、用語の意味を変えたら docs 全体を grep する（試行）

P5 の振り返りで、2回目になった候補を2つ決めた。どちらもプランを作る手順（手順1）で防ぐ。試行なので、次の画面のサイクルで効いたかを振り返りで見る。

- 画面に出るもの（配置・見た目・文言・操作）を決める・スコープ外にするときは、ASCII の配置図を示して人間に選んでもらい、選んだ図を「人間に確かめたこと」に載せる。プランのレビュー（設計整合）は、図が無ければ P1 にする。Claude Code では `AskUserQuestion` の `preview` に図を入れる（`dev-cycle` スキル）
- 用語の意味を変えるときは、grep の範囲を `docs/cartagraph/`・用語集から、`docs/` 全体（`plans/`・`process/evolution*` を除く）と `AGENTS.md` に広げ、直す箇所と残す箇所の一覧をプランに書く

採らなかった案：用語集の項目を変えたコミットで、その言葉を使うページを機械で挙げる（`check-terms.mjs` の拡張）。意味が変わったかどうかは文字の差分から決まらず、挙げるだけでは振り分けは人がする。手順で3回目が起きたら考える。

- **きっかけ** — 人間レビュー（P4・P5 の配置の差し戻し）と AI レビュー（P1・P5 の用語の取りこぼし） ／ **止め方** — 手順・ルール（`docs/process/index.md` の手順1、依頼文「1」「2」、`dev-cycle` スキル）。機械で挙げる案は、3回目が起きたら考える

### 2026-10-31 シナリオのデータの置き場所を決め、ライトの線をファイルで引く

P4（試験の最初のシーン）で最初のシナリオの JSON を作るので、core-loop で決めることになっていた置き場所を決めた。`packages/domain/src/scenario/` の `*.json` に置き、同じ名前の `.ts` が zod で読んで書き出す（`package.json` の `exports` が `.ts` だけを指すため。読むすべての経路で参照の切れが止まる）。データもスキーマも `packages/domain` に入るので、「シナリオのデータの中身だけを直す変更はライト」の線を、`*.json` だけならライト、`.ts` を伴えばフル、とファイルで引いた。`testing.md`「テストのデータ」と `docs/process/index.md`「適用範囲」を直した。

### 2026-10-31 依存の古さと脆弱性を、CI が月に1回知らせる

P3（依存の版を上げる）の振り返りで、預かっていた候補「依存の版が、気づかないうちに古くなる」を決めた。P3 では版を上げるたびに設定やテストの直しが要った（Biome のルール、redocly のオプション、TypeScript の `baseUrl`、Vite のチャンク分け、Vitest の出力先）。自動で PR を作っても、そのまま取り込める回は少ない。そこで、CI が月に1回 `pnpm outdated -r` と `pnpm audit` を流し、結果を1つの Issue に書き換える形にした。版上げはその Issue を見て要望にし、1サイクルで回す。ワークフローは要望 `docs/backlog/dependency-watch.md` で作る。

採らなかった案：Dependabot・Renovate で PR を週ごとに作る（メジャーの更新は人とエージェントの手が要り、PR が増えるだけ）。却下して、思い立ったときに要望を立てる（P1 のように差が溜まる）。

- **きっかけ** — 作業中の失敗（P1 の R2・R4）と人間の判断（P3 の振り返り） ／ **止め方** — 機械（CI の月1回の定期実行）。ワークフローは要望 dependency-watch で作る

### 2026-10-30 手順の終わりでは、報告の前に、プランの更新・コミット・次の説明まで済ませる

P3 の実装の AI レビューを終えたとき、エージェントが結果を報告して「プランの状態を直してコミットしますか」と聞いた。人間は「そこまでやってから聞いてほしかった」と指摘した。区切りの決まり（「セッションを分ける」）は 2〜3 と 8 のスキルの節にだけあり、6 の終わりから 7 へ移るところに書いていなかった。エージェントの癖でもあるので、エージェントごと・PC ごとの記憶（自動メモリ）ではなく、`docs/process/index.md` に書いた。

`docs/process/index.md` に「手順の終わりでは、報告の前に、次に要ることを済ませる」を足した。手順を終えたら、報告の前に、プランの状態の行・手順の結果（手順6の終わりは人間レビューの説明も）・コミットを済ませ、人間に聞くのは人間の判断が要ることだけにする。`dev-cycle` スキルの手順6に、この節を指す1文を足した。

- **きっかけ** — 人間レビュー（P3 の実装のレビューの途中での指摘） ／ **止め方** — 手順・ルール（`docs/process/index.md`、`dev-cycle` スキル）。機械では止めない：報告の前かどうかは、ツールの呼び出しの並びから判別できない。同じ指摘が2回目に出たら、Claude Code のフック（Stop 時にプランの状態の行とコミットの有無を見る）を考える

### 2026-10-30 テストの書き方の lint（Biome 2.6 の3ルール）を error で効かせる

Biome を 2.6.3 に上げると、テストの lint に新しいルール（`useConsistentTestIt`・`useExpect`・`noConditionalExpect`）が入り、既存のテスト48件が当たった。既定の重さ（info・warning）では違反してもコミットも CI も止まらないので、テストの override で `error` に上げ、当たるテストを直した。Playwright は `it` を持たないので、`apps/web/e2e/**` だけ `test` を好む設定にした。直した後に、守っている条件が抜けていないことを、本体の検査を1つずつ外して書き換えの前後で比べて確かめた（`trace.mjs` の `fail` のうち2件は書き換え前から落ちない。テストの書き換えで増えたものではない）。Markdown の整形は入れず、lint だけかける。

- **きっかけ** — 作業中の失敗（依存の版の更新 P3 で、新しいルールが既存のテストに当たった） ／ **止め方** — 機械（`biome.json` のテストの override。`pnpm lint`・pre-commit）

### 2026-10-30 文書が、無いスクリプト・検査・pnpm のスクリプトを指したら止める

P1 の振り返りで採用した。P1 の AI レビューで、消した・持ち込まなかった検査を文書が指したままの指摘が3件続いた。A2：スキルが置いていった `check-plan-pr-draft`・`web:check:*` を「止める」と書いていた。A7：部品としてだけ置いたスクリプトのコメントが、流れている前提のままだった。B1：A3 で外した biome の override を `architecture.md` が案内していた。前のリポジトリでも同じ種類があった（2026-10-27 の候補。関数を移したのに、文書の「`関数名`（`ファイル`）」が古いまま）ので、2回目として仕組みにした。

`scripts/check-doc-refs.mjs` を `pnpm docs:build` で流す。docs・`.claude/`・`AGENTS.md` の Markdown のコードの部分から、`scripts/…` などのパス・`xxx.mjs`・`check-xxx`・`pnpm <スクリプト>` を拾い、実在しなければ止める。経緯の記録（plans・進化ログ）と、まだ無いものを書く場所（要望・デザイナーノート）は見ない。持ち込まなかったものをわざと指す行は、「前のリポジトリ」と書けば見ない。入れたときに、`testing.md` の `check-rule-test-exclusions.mjs` が1件見つかったので、この書き方に直した。B1 の種類（設定の中身の指し先）と、前のリポジトリの案の「`識別子`（`パス`）」の組は見ていない。

- **きっかけ** — AI レビュー ／ **止め方** — 機械（`pnpm docs:build` の `scripts/check-doc-refs.mjs`）。B1 の種類と「`識別子`（`パス`）」の組は、また起きたら足す

### 2026-10-30 持ち込んだルール・スキルから、元のゲームの例と置いていった検査への言及を消した

P1 の実装の AI レビューで、`docs/process/` の例（GM 不在の進行・自動戦闘・`SC-1` など）と、スキルの「`check-plan-pr-draft` が止める」が残っていると指摘された。無い検査を「止める」と書くと、エージェントが止まるはずだと信じて通す。例はこのゲームの言葉（PL-1・手札・シーン）に置き換え、言及は消した。用語の旧称の一覧（`check-terms.mjs`）も元のゲームのものだったので空にした。

- **きっかけ** — AI レビュー ／ **止め方** — 手順・ルール（書き換えた）

## 却下

### 2026-10-30 開発の速さの足を引っ張る検査は、新しいリポジトリへ持ち込まない

リスクを許して、まず進める（人間の判断）。次の検査は持ち込まず、括弧の中のことが起きたら要望にして足す。

- `check-spec-paths`（正式仕様のページに書いた実装のパスが古くなる事故が起きたら）
- `check-provisional` と仮ルールのページ（仮ルールを置きたくなったら）
- `check-suppressions`（biome-ignore が増えて、理由の管理が要るようになったら）
- `check-biome-layers`（FSD の層をまたぐ import の事故が起きたら。`biome.json` の層の禁止そのものは持ち込んだ）
- `check-rule-test-exclusions` とルールの節ごとの結果のページ（ルールのページが増えて、節ごとの結果を見たくなったら。トレースが部品として使う `build-rule-test-report.mjs`・`check-provisional.mjs` は、検査としては流さずに持ち込んだ）
- `check-plan-pr-draft`（プランの PR 下書きの漏れが続いたら）
- MSW と、MSW のハンドラと API の一覧を照らすテスト（画面から API を叩くようになったら）

- **きっかけ** — 人間の要望 ／ **止め方** — 手順・ルール（足すきっかけを、この項目とプランに書いた）
